CORNERCOACH DATA COLLECTION AND SOURCE-INDEPENDENT BENCHMARK PLAN
Version 1.0 - 4 October 2026

PURPOSE
=======

This document explains how to build the next dataset for punch detection,
punch classification, hand classification, and guard-discipline analysis.
It focuses only on collecting, labeling, splitting, and checking data.

The production target is CPU inference. Data extraction and model training may
use a GPU. The plan therefore keeps the production input pose-based and does
not depend on a large video model that would be impractical on a CPU.


THE SHORT ANSWER
================

Yes, record your own videos. However, do not put every recording into one
dataset. Create three separate pools before training:

1. DEVELOPMENT POOL
   Used for training, validation, threshold calibration, error analysis, and
   hard-negative mining.

2. INTERNAL TEST SET
   Contains unseen boxers and/or unseen recording sessions. Use it only at
   important milestones, not after every experiment.

3. LOCKED PRODUCTION BENCHMARK
   Contains completely independent videos. Never use these videos for
   training, validation, early stopping, normalization statistics, selecting
   the confidence threshold, hard-negative mining, or feature design. Run this
   benchmark only after the model and all decision rules have been frozen.

If benchmark results influence a model change, that benchmark is no longer a
fair final benchmark. Retire it into the development/test pool and create a
new locked benchmark for the next final evaluation.

Licensed open-source videos are useful because they add new cameras, people,
lighting, backgrounds, and filming styles. Record the source URL and license.
Do not use a random online video unless its license permits your intended use.
All clips cut from one original online video must remain in the same data pool
and split.


1. DEFINE THE TASK BEFORE RECORDING
===================================

The model needs to answer three separate questions:

- Is a real punch happening now, or is this non-punch movement/background?
- If it is a punch, which hand threw it: left or right?
- If it is a punch, what is its type: jab, cross, hook, or uppercut?

Treat "background" as a real, deliberately collected class. It must not mean
"anything that was not annotated." An unlabeled interval may contain a missed
punch, so a reviewer should confirm negative intervals.

For straight punches, use boxing role and stance:

- Jab = a straight punch by the lead hand.
- Cross = a straight punch by the rear hand.

This matters because the same physical left hand can be the lead hand in an
orthodox stance or the rear hand in a southpaw stance. Hand, stance, role, and
trajectory should be recorded separately instead of being inferred from hand
alone.


2. RECORDING PLAN
=================

Record original videos, not augmented videos. Apply mirroring, brightness,
speed, and other augmentation only after data splitting.

Recommended capture settings:

- Record at 1080p when possible; use a constant 30 FPS. Sixty FPS is also
  acceptable if FPS is saved and all timestamp conversion is correct.
- Use enough light and a fast enough shutter to reduce fist motion blur.
- Keep the boxer, shoulders, elbows, wrists, hips, and head visible.
- Keep the camera fixed for most recordings, but deliberately collect a small
  camera-motion subset as hard-negative or robustness data.
- Save the untouched original file. Do not repeatedly re-encode it.
- Give each boxer a non-identifying ID and obtain permission/consent.

Collect variation that resembles production:

- Different people, body sizes, skill levels, clothing, and glove colors.
- Orthodox and southpaw boxers; switching stance if that is in scope.
- Different rooms, gyms, backgrounds, lighting, and camera quality.
- Front, approximately 30-45 degree, and side views that your app will accept.
- Different distances and moderate partial occlusion.
- Shadowboxing, bag work, pad work, and sparring only if each will be supported
  in the product. If production is only shadowboxing, make that explicit.

Suggested session structure for each boxer:

A. Calibration and stance
   10-15 seconds standing naturally in guard in each supported stance.

B. Isolated punches
   At least 10 clean repetitions of every valid punch combination, resetting
   to guard between repetitions. Record slow, normal, and fast examples.

C. Combinations
   Record realistic two-, three-, and four-punch combinations. Include short
   gaps, overlapping recovery, and changes in speed.

D. Hard negatives
   Record 30-60 second blocks of each important non-punch movement listed in
   Section 5.

E. Natural sequence
   Record several minutes without a script. The boxer should move naturally,
   rest, adjust guard, feint, defend, and punch. This reveals errors that a
   clean repetition drill will hide.

Do not count mirrored or color-adjusted copies as new real examples. Dataset
counts should always distinguish original motions from augmented descendants.


3. HOW MUCH DATA TO COLLECT
===========================

The present data has only three source videos and 93 original positive events.
The many augmented copies do not create new people, motion styles, recording
conditions, or independent evidence. More independent source data is the main
priority.

A practical first milestone is:

- 15 or more boxers if possible, with at least two sessions on different days.
- At least 75-100 original events for each of the eight hand/type combinations.
- Prefer approximately 200 original events per combination (about 1,600 total)
  before treating the classifier as production-oriented.
- A stronger later target is 500 original events per combination and at least
  20 different boxers.
- Collect 3-5 times as much raw hard-negative time as positive-event time.
  During dataset building, sample this negative data in a balanced way rather
  than using every almost-identical idle frame.

These are starting targets, not guarantees. Stop using only class totals as a
quality measure: independent boxers, sessions, environments, and difficult
examples matter more than thousands of copies of the same movement.

If collecting 15 people is initially impossible, create a pilot with 5-8
people, but report it as a pilot. Use leave-one-boxer-out evaluation and do not
claim source-independent production accuracy from it.


4. POSITIVE PUNCH ANNOTATION
============================

Annotate a temporal event with three important frames:

- start_frame: the punching hand leaves a stable guard or begins committed
  outward acceleration.
- apex_frame: maximum extension, impact/contact proxy, or the point where the
  outward direction reverses.
- end_frame: the hand returns to guard or clearly completes recovery.

For combinations, create one event per punch. Separate consecutive punches at
the new punch onset/direction change. Temporal overlap is allowed if one hand
begins while the previous hand is recovering.

Record at least these fields for every punch:

event_id
source_video_id
boxer_id
session_id
camera_id
camera_view
fps
start_frame
apex_frame
end_frame
start_timestamp_ms
apex_timestamp_ms
end_timestamp_ms
stance_at_apex                 orthodox / southpaw / switch / unknown
stance_confidence              high / medium / low
anatomical_hand                left / right
boxing_role                    lead / rear / unknown
trajectory                     straight / hook / uppercut
final_punch_type               jab / cross / hook / uppercut
occlusion_level                none / partial / severe
motion_blur                    none / moderate / severe
annotation_quality             accepted / ambiguous / rejected
reviewer_id
dataset_role                   train / validation / test / benchmark_locked

Keep ambiguous examples, but mark them. Do not force them into a clean class.
They can be excluded from supervised training and retained for later review or
robustness analysis.


5. BACKGROUND, IDLE, AND HARD-NEGATIVE ANNOTATION
=================================================

Yes, deliberately record and label intervals where no punch is thrown. This is
essential because the current false positives come from movements that look
partly like a punch. Do not create only one vague pile of background data.
Keep a background subtype for analysis, while mapping all subtypes to the
model's background/no-punch target.

Recommended negative subtypes:

- background_idle_guard
- background_hands_down_or_relaxed
- background_footwork
- background_head_movement
- background_slip_duck_weave
- background_block_parry
- background_feint
- background_guard_adjustment
- background_glove_or_face_touch
- background_non_punch_arm_motion
- background_stretching_or_warmup
- background_recovery_between_punches
- background_person_entering_or_leaving
- background_partial_occlusion
- background_pose_or_tracking_failure
- background_camera_motion
- background_bag_or_other_person_motion

For every confirmed negative interval, record:

negative_interval_id
source_video_id
start_frame
end_frame
background_subtype
stance
boxer_id
session_id
camera_view
difficulty                    easy / medium / hard
reviewer_id
dataset_role

Leave a small exclusion margin, initially about 3-5 frames, around uncertain
punch boundaries so transition frames do not become incorrectly labeled
background. Once start/apex/end annotations are reliable, intentionally keep a
separate set of recovery and near-punch negatives because these are valuable
hard cases.

After training a first model, run it over DEVELOPMENT negative videos. Review
its false positives and add the confirmed mistakes as hard negatives. Never
mine mistakes from the locked benchmark; doing that leaks the benchmark into
development.


6. STANCE LABELING AND ROBOFLOW WORKFLOW
========================================

Stance should be labeled, but it should not become part of the punch class
name. Do not create classes such as "orthodox_left_jab" and
"southpaw_left_jab". That creates too many sparse classes.

Recommended approach:

1. Keep the existing eight positive event labels for compatibility:
   left_hand_jab, left_hand_cross, left_hand_hook, left_hand_uppercut,
   right_hand_jab, right_hand_cross, right_hand_hook, right_hand_uppercut.

2. Store stance as a separate interval/attribute:
   orthodox, southpaw, switch, or unknown.

3. Store anatomical hand, boxing role, and trajectory as separate fields in
   the canonical annotation manifest. The final punch type can be checked from
   them. For example, lead + straight must be jab; rear + straight must be
   cross.

4. If stance changes during a video, end the current stance interval and start
   another. Do not assign one stance to the entire video unless it is true for
   the whole video.

5. If stance is hidden or unclear, use unknown. Do not guess. Mark the punch
   ambiguous if jab versus cross cannot be determined reliably.

Roboflow can remain the visual annotation tool, but maintain a canonical CSV or
JSON outside Roboflow for temporal fields and audit history. Roboflow video
uploads are sampled into images/frames, so keep the original video ID, decoded
frame number, timestamp, and FPS in your manifest. Never depend only on the
displayed Roboflow frame number.

Useful Roboflow per-image metadata/tags, when supported by the export:

- source_video_id
- boxer_id
- session_id
- camera_id and camera_view
- stance
- fps
- dataset_role
- license_id
- annotation_reviewed

Annotate original videos once. Do not upload and independently annotate every
mirrored or augmented copy. Generated variants must inherit the original event
timing and split. Mirroring swaps anatomical left/right labels and lead/rear
only according to the defined transformation rules.

For negative intervals, you do not need to draw a person box on every frame if
YOLO supplies the person/pose detection. Instead, confirm the time interval and
assign its negative subtype in background_intervals.csv. If your Roboflow
project cannot preserve these temporal attributes cleanly, keep them in the
companion CSV rather than squeezing them into object classes.


7. SPLITS THAT PREVENT DATA LEAKAGE
===================================

Never split individual frames or punch events randomly. Related frames are
almost duplicates, and that would make reported accuracy misleading.

Use a group key containing at least:

boxer_id + session_id + source_video_id

Prefer splitting by boxer. A person in validation or test should not occur in
training. If that is temporarily impossible, split by complete session and
clearly call the result session-independent rather than boxer-independent.

Recommended development allocation:

- Training: 70% of development groups.
- Validation/calibration: 15% of development groups.
- Internal test: 15% of development groups.
- Locked benchmark: a separate pool, not part of the percentages above.

All clips, frames, mirrored files, speed changes, and other augmented
descendants from one source must inherit its group and split. Use augmentation
only in training. Evaluate validation, test, and benchmark on original,
unmirrored video.

The following must be calculated from training data only:

- Feature normalization statistics.
- Class weights.
- Interpolation or missing-data rules that are learned from data.

Choose confidence thresholds and other decision rules on the validation/
calibration set. Do not choose them from the internal test or locked benchmark.


8. SOURCE-INDEPENDENT PRODUCTION BENCHMARK
==========================================

Build this benchmark before the final model is selected, then lock it.

Recommended minimum design:

- At least 5 completely unseen boxers; more is better.
- People, sessions, camera setups, and source videos absent from development.
- Both orthodox and southpaw stance when possible.
- All eight hand/type combinations, plus long continuous negative sections.
- Isolated punches, combinations, realistic idle time, feints, defense, and
  the difficult negative movements from Section 5.
- Original, unaugmented, unmirrored video only.
- A mixture of your controlled recordings and separately licensed external
  videos, reported both separately and together.

Keep benchmark files in a physically separate read-only directory. Do not run
exploratory predictions over it. Ideally, keep its gold annotations separate
from the everyday development environment and reveal them only to the final
evaluation script.

Report event-level metrics, not only frame accuracy:

- Punch event precision, recall, and F1.
- False positive punches per minute of no-punch video.
- Hand accuracy on correctly detected punch events.
- Punch-type macro-F1 on correctly detected punch events.
- Exact hand-and-type accuracy.
- Per-class recall for all eight combinations.
- Performance by boxer, stance, camera view, lighting, speed, and negative
  subtype.
- CPU processing FPS, median latency, and peak memory on the intended machine.

Use an event matching rule decided before evaluation, for example: a predicted
event matches a gold event when its peak lies inside the annotated event or
when temporal intersection-over-union exceeds a fixed value. Count clustered
predictions for one physical punch as one event, not many frame detections.


9. QUALITY CONTROL
==================

Annotation quality is as important as quantity.

- Write a one-page visual labeling guide with examples for each class.
- Double-label at least 10% of the data using two reviewers.
- Resolve any hand/type/stance disagreement and start/apex/end disagreements
  larger than two frames.
- Automatically check start_frame <= apex_frame <= end_frame.
- Flag unusually short or long events for review instead of silently deleting
  them. A starting review range could be 3-20 frames at 30 FPS, but fast and
  slow examples can legitimately fall outside it.
- Check that jab is lead-straight and cross is rear-straight.
- Inspect random samples from every class, boxer, session, view, and split.
- Track severe occlusion, blur, and missing pose separately.
- Preserve an audit trail when a label is changed.

Create a versioned dataset card containing:

- Collection dates and consent status.
- Intended production scenarios and excluded scenarios.
- Boxer/session/view/stance counts.
- Event and negative-subtype counts.
- Split policy and group IDs.
- Known weaknesses and annotation uncertainty.
- Source licenses and URLs.
- Dataset version and file hashes.


10. CURRENT POSE QUALITY AND CPU CONSTRAINTS
============================================

The pose/crop audit is acceptable, though not excellent. Therefore:

- Keep YOLO11s pose for the next data version; changing the base pose model is
  not the first priority.
- Store pose confidence, crop confidence, missing joints, blur, and occlusion
  so later errors can be separated into pose failures and classifier failures.
- Save a small pose-failure review set. Reconsider the pose model only if error
  analysis shows it is a major bottleneck.
- Use the same preprocessing, keypoint order, normalization, and image size in
  extraction and production.
- GPU extraction/training is fine. It does not require the production runtime
  to use a GPU.

The pose detector is likely to dominate CPU time; the LSTM or small ST-GCN is
comparatively inexpensive. Keep the production plan pose + kinematics first.
After the new data is ready, retrain both existing networks and select using
event metrics plus real CPU speed. A small temporal convolutional network can
also be tested later because it is CPU-friendly, but it is not a substitute
for fixing the dataset.

Do not make a heavy RGB video network such as SlowFast, PoseC3D, or a large
two-stream model a production dependency. If pose-only performance eventually
plateaus, an optional lightweight cropped-RGB branch may be tested only after
it meets a written CPU latency and memory budget on the target computer.

Because real punches may last only 5-8 frames, keep precise start/apex/end
labels. Those annotations allow later comparison of 5-, 7-, and 11-frame
causal windows without relabeling. Eleven frames can remain the initial model
window, but the data should not bake in one fixed window size.

12. STEP-BY-STEP EXECUTION ORDER
================================

Step 1 - Freeze the label guide
Define punch boundaries, jab/cross by lead/rear role, stance values, ambiguous
cases, and background subtypes. Give the same guide to every annotator.

Step 2 - Create IDs and manifests
Create boxer, session, video, camera, consent, and license IDs before files are
uploaded or renamed.

Step 3 - Record a small pilot
Record two or three people and all session blocks. Annotate them completely.
Confirm that pose, timestamps, and labels can be exported correctly.

Step 4 - Fix the collection protocol
Correct camera placement, lighting, label definitions, or missing negative
movements discovered in the pilot. Avoid changing definitions halfway through
the main collection.

Step 5 - Record the development pool
Prioritize new people and sessions over more repetitions from the same person.
Collect positives, natural sequences, and deliberate hard negatives.

Step 6 - Create group-based splits
Assign boxers/sessions/source videos before augmentation. Check that no source
or person crosses an inappropriate boundary.

Step 7 - Build and lock the benchmark
Use separate unseen people and external licensed sources. Finish gold labels,
write its manifest, hash the files, and make the directory read-only.

Step 8 - Perform annotation QA
Double-label 10%, run consistency checks, resolve disagreements, and publish
dataset counts by original source rather than augmented file count.

Step 9 - Extract pose data on the GPU
Use the existing YOLO11s pipeline. Save quality flags and retain failed frames
as missing data instead of fabricating zero-coordinate detections.

Step 10 - Train later, after the data release is frozen
Training, confidence calibration, and hard-negative mining use development
data only. CPU production speed is measured on the target CPU before choosing
the final network.

Step 11 - Run the locked benchmark once per frozen release
Save the exact model hash, settings, metrics, CPU specification, latency, and
benchmark version. Do not tune using this result.

[ ] Every file has boxer, session, source, camera, and license/consent IDs.
[ ] Splits are by boxer/session/source, never by random frames.
